## 2. 分层职责（核心分工原则的落地）

| 层 | 模块 | 职责 | 明确不做 |
|---|---|---|---|
| 数据系统 | services/ | 提供事实（受控读/写） | 不做决策 |
| 传统算法 | agents/stats.py + perception | 发现与计算（异常检测） | 不做解释叙述 |
| 知识库 | data/kb/*.yaml | 规则（指标/治理/根因/打法） | — |
| 大模型 | agents/llm.py | 理解与叙述（仅引用事实数字） | 不计算、不决定高风险 |
| Agent | agents/* | 跨工具编排 + trace 贯穿 | 不绕过治理 |
| 业务系统 | services/ 写接口 | 最终执行（幂等/审计/补偿） | 不越过 Policy |
| 治理 | governance/ | 控制风险（L0-L4/审批/审计） | — |
| 评估 | agents/evaluation.py | 验证价值（真实指标复盘） | 不评文本相似度 |

## 3. 数据流（一条异常的生命周期）

1. **感知**：`perception.scan()` 批量取 42 天销售矩阵 → 基线（前28天滚动中位数+MAD）→ 近14天逐日 z-score/比例规则 → 连续≥2天异常段 → `anomalies` 表（证据=工具返回快照，检测时效=窗口起点至今）
2. **诊断**：9 类假设并行验证，每类调用只读工具取数 → 证据≥2 且方向相容者入选 → 按置信度排序取 Top3（贡献度归一化）→ `diagnoses`（含 hypothesis_log 工具调用记录，可审计）
3. **决策**：`playbooks.yaml` 按（异常类型 × 根因）查打法 → 构建动作参数（补货量=μ×覆盖天数向上取整到 MOQ 倍数）→ 约束检查（不通过即丢弃，约束违反率 0）→ ROI 估算（参数=世界因果模型）→ Policy Engine 定风险/审批 → `decision_cards`
4. **执行**：低风险（requires_approval=0）自动执行；高风险仅创建 `approvals`；执行时 Policy 二次校验（纵深防御）+ 幂等键=决策卡ID → 业务系统写接口 → `executions`（状态机）
5. **治理**：审批中心（L3 风控）决定 → 通过后执行携带审批单号；全程 `audit_logs`（同 trace_id 串起七层）
6. **评估**：`world/advance_days` 按因果规则推演 T+N（到货增加现货、促销弹性=1+折扣×6、销量受库存门控、客服任务降低客诉率）→ `evaluation.review_execution` 对比执行前后 7 天真实指标 → verdict + 原因 → 更新 `strategy_weights`

## 4. 关键设计决策

- **单库分域而非微服务**：六大 Mock 系统以独立表域 + 独立路由前缀呈现，本地零配置可跑；表/路由边界即微服务拆分线（如需拆分，按域包一层即可）
- **稀疏存储 + 补零**：sales 粒度=门店×SKU×天，零销量不落行，读取时按日期补零（1.6M 行承载 2.8M 组合）
- **BaselineMu 表**：生成器把每个门店×SKU 的基线需求 μ 落表，时间推演器复用同一因果模型，保证"复盘基于同一世界假设"
- **LLM 防编造**：叙述生成后做数字校验，出现事实表之外的数字→回退模板叙述（governance 保证）
- **expire_on_commit=False**：SQLModel 会话在 commit 后保持对象可读，避免序列化空对象
- **trace_id 贯穿**：perception→…→evaluation 全部带 trace，审计日志一键还原案例链路

## 5. 定时任务

`RETAIL_SCHEDULER=1` 时启用 APScheduler：每小时执行一次感知扫描（`perception.scan`），新异常进入后续流水线（可由人工或自动化触发 `/api/agent/pipeline`）。
