## 1. 总结论

**系统满足原问题。** R1–R5 五条需求经三方审计均判"满足"，独立复核无一推翻；本人复跑测试套件 39 项全绿，五条需求各自有直接承载模块与对应测试（见第 2 节裁决表）。系统是一个**可运行的、过审的、但明显超纲的**答卷。

**超纲程度：约占非测试源码的 35%–40%（约 2500 行 / 6659 行），约 1/3 的模块域以超纲内容为主导。**

| 口径 | 计算 | 结果 |
|---|---|---|
| 纯演示/评估超纲 | world injector 228 + timemachine 189 + agents 超纲 420（evaluation 219 / llm 113 / orchestrator 演示闭环 / governance_agent 34）+ api/world 51 + scripts 演示部分 ~188 | ~1090 行 |
| 可见性超纲 | web 915 行（原问题无任何 UI 要求；记 300 行最小可见性额度后净超 ~615）+ api/agent.py KPI/指标路由 ~80 + metrics.yaml 指标字典大部 ~200 | ~900 行 |
| 核心模块内嵌超纲 | execution 补偿 ~40 + decision 三个额外动作分支 ~90 + 幂等写入 99（强化项） | ~230 行 |
| **合计** | — | **~2500 行 ≈ 非测试源码 6659 行的 38%**（区间 35%–40% 取决于给前端记多少可见性额度） |

模块域视角：services / api / agents / governance / world / web / scripts / kb / models+core / tests 共 10 个模块域，其中 **world（894 行）、web 大部（915 行）、scripts 大部、agents 的 evaluation/llm 半壁（420 行）** 约 3.5 个域由超纲内容主导。

**超纲的定性**：超纲不等于错误，要分两档看——

- **工程强化型超纲（方向正确，保留）**：幂等写入、补偿、全链路审计 trace 是 R5"约束机制"的纵深实现，仓库自述为"写操作四保险"（README），属于把 R5 做扎实而非做偏。
- **演示叙事型超纲（概念负担重，隔离）**：世界时间机器 + T+7 复盘 + 策略权重自学习构成一条"自我进化"演示闭环，引入了 `promo_lift_coef=6` 三处硬编码一致（timemachine.py:125 / decision.py:147 / playbooks.yaml:93）等耦合，是全系统概念负担最重的部分，与 R1–R5 无一条直接相关。

### 特别裁决：调拨 / 会员触达 / 客服跟进三类动作的去留

**裁决原则**：R4 只点名补货与促销，三类动作均不属于最小必需集——这一点上原盘点正确；但"不属于最小集"不等于"可无损砍除"，独立复核已用代码事实证伪了"零成本砍除"的主张。产品决策的正确姿势是**冻结而非切除**：

| 动作 | 裁决 | 关键事实（本人核实） | 若未来要真砍的先决条件 |
|---|---|---|---|
| transfer 调拨 | **降级为可选** | weather 根因唯一打法（playbooks.yaml:68-73）；5 处治理测试依赖；跨区审批是 R5 约束机制的最佳演示载体 | ①weather 场景补配 replenish 打法；②跨区审批测试改走促销超限路径；③同步收缩 3 个测试文件 |
| member_reach 会员触达 | **降级为可选** | member_churn 根因唯一打法（playbooks.yaml:62-67），砍掉则该场景诊断→决策断链；docs/01:38,40,41 场景矩阵点名 | ①member_churn 场景补配 promo 打法；②改 execution TOOL_MAP / policies.yaml / evaluation ROI 分支；③修订 docs/01 场景矩阵 |
| cs_followup 客服跟进 | **降级为可选** | test_ticket_task_and_external 直连 /api/cs/tasks（tests/test_mock_systems.py:173-189）；docs/01:37,42 场景矩阵点名"客服跟进" | ①删该测试或改为只读断言；②删 timemachine 客服整改因果规则；③修订 docs/01 场景矩阵 |

**共同结论**：三者合计约 130 行决策分支 + 少量服务代码，净维护成本低；动刀的连带成本（打法库补配、测试收缩、文档修订、链路断链风险）高于留着的成本。**本轮一律冻结投入、保留代码**；它们是否出现在系统里，由 playbooks.yaml 的触发配置决定——把这三个触发注释掉，决策层即不再产出这三类卡，代码零删除。这比物理切除更符合"最小化"且可逆。

## 4. 精简蓝图与裁剪路径

### 4.1 若只按原问题最小重做，系统应该长什么样

最小系统 = 六个模块 + 一份测试，估计 **~2200 行**（约为现有非测试源码 6659 行的 1/3）：

### 4.2 从现有系统裁剪到蓝图的路径（四步，每步独立可验收）

**第 0 步 · 还债（不改任何行为）**
- 角色权限收敛单源：`data/kb/metrics.yaml` 为唯一来源，auth.py 启动时读取（消除双源不一致：auth.py 多出 system:L4）。
- 修复 check_data_scope 区域经理范围未实现的注释-实现偏差。
- governance_agent.py 34 行薄层并入 execution.py。
- 验收：pytest 39 项全绿不变。

**第 1 步 · 概念隔离（feature flag，不删代码）**
- world/injector/timemachine/evaluation 复盘/llm/demo 脚本归入 `RETAIL_DEMO=1` 可选包；默认路径不含这些概念。
- 调度器翻转为默认开（RETAIL_SCHEDULER=1 为默认，演示场景显式关）——R2 名分归位。
- 验收：`RETAIL_DEMO=0` 时服务启动、R1–R5 主链路（扫描→诊断→决策→执行→审批）完整可用；`RETAIL_DEMO=1` 时现有演示与全部测试照常。

**第 2 步 · UI 收缩 + 交互 P0**
- 9 页 → 6 页：砍世界页与复盘页推演按钮（复盘页降为只读报告或并入审计视角）；同步收缩 e2e 第 8 步（test_e2e_playwright.py:148-153）。
- 落地交互 P0 四件：角色切换即生效、漏斗化闭环条、审批工作台、轮询角标。
- 验收：e2e（收缩后）通过；审批操作全程备注留痕。

**第 3 步 · 动作收缩（仅当确要最小化时执行）**
- transfer/member_reach/cs_followup：**先改配置后动代码**——注释 playbooks.yaml 对应触发，决策层即不再产出这三类卡；代码与测试保留（治理测试依赖 transfer 跨区路径，须先按第 2 节先决条件改道）。

- 验收：收缩后 pytest 与 docs/01 场景矩阵声明同步更新，不留文档-代码矛盾。

**明确不做的**：物理删除 evaluation/world 模块。依赖面（conftest 世界夹具、test_world 6 用例、test_8/test_9/test_10、e2e、docs/05 验收要点、demo 脚本）证明删除成本 > 收益，隔离即可达成同样的概念减负。

## 5. 结论一句话

**答卷合格且过量**：R1–R5 五条全数满足、39 项测试全绿、治理纵深扎实；代价是约 38% 的代码与约三分之一的概念花在了原问题从未要求的世界推演、复盘自学习、九页看板与演示基建上。建议按"还债 → 隔离 → UI 收缩 → 配置级动作收缩"四步走完裁剪路径，全程不物理删码、每步可验收，最终收敛为一个 ~2200 行、概念密度翻倍的最小系统。
